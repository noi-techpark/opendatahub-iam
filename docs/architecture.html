Open Data Hub · identity service

Who do the APIs trust, and where does the service sit

The identity service is the only issuer the APIs know, and the hook at the edge is the identity-aware proxy. Part one is the design and every kind of caller, inside and outside the cluster. Part two is how it lands on the existing infrastructure, what changes per repository, and the effort.

State of the PoC. The repository implements the hook end to end, with an nginx auth_request dev edge, the service key in a header, and passing API and browser suites. The claim set below, the client_credentials token endpoint (POST /v1/token) and the pass-through of the service's own JWT at the hook are implemented and covered by the suites. Since 2026-11-19 the repository noi-techpark/opendatahub-iam also carries the production layer: JSON logs and OpenTelemetry through the Go SDK, a rate limit on the credential-relaying routes, a readiness probe, versioned migrations, signing key rotation through a key directory, and an operator view over tokens. Not yet: a load test of the Keycloak admin path, the helmfile and sops deployment.

Part one · the design

One issuer, a hook at the edge

Decided 2026-10-23: the gateway topology. The identity service is the only token issuer the APIs know. Every request to an API passes an authorization step at the edge, where the proxy asks the service to resolve whatever credential arrived (Keycloak token, API token, nothing) and forwards the request with a JWT the service signed. Keycloak still logs users in, authenticates machine clients and holds role assignments; its tokens stop at the edge. The hook is the identity-aware proxy: the decision half lives in the service, the proxy half is whatever already fronts the API.

The hook

auth_request (nginx), forward_auth (Caddy), forwardAuth (Traefik) and ext_authz (Envoy) are one mechanism: before proxying, the proxy sends the client's headers to a URL, a 2xx means proxy and copy the named headers onto the request, a 401 or 403 goes back to the client, anything else is a 500. The proxy keeps no session and does this on every request. The service only ever sees headers, never a body.

The token endpoint

A hook converts a credential that arrives with a request. A caller that never passes a proxy, such as a transformer writing to bdp-core over cluster DNS, needs the conversion ahead of time. The service therefore also offers a standard client_credentials token endpoint and acts as a broker in front of Keycloak's.

  • The response is the standard access_token, token_type, expires_in body that golang.org/x/oauth2/clientcredentials and Spring's client registration expect. Nothing else on the caller changes.
  • The JWT carries the same claims the hook produces: subject, azp set to the client id, roles per client, principal kind client. Its audience is what Keycloak's would be plus every configured API, so one token serves bdp-core and ninja-api as a Keycloak token does today; roles decide what it may do there, as now. No user data. Machine tokens can live minutes instead of 60 s.
  • Disabling the client in Keycloak stops its next renewal. A role change reaches it at the next renewal or the cache window, whichever is later.
  • Because such a JWT is a legitimate credential, the hook passes it through when the signature and audience check out. The PoC rejects it today and has a test saying so; that test flips.

What must hold

  1. An API verifies JWTs from the identity service and from nobody else.
  2. Every request to an API either passed a hook or already carries a service JWT. A path around the hook yields only anonymous access, since a Keycloak token sent straight to the API fails verification, but it must not exist for a protected deployment.
  3. Whoever obtains a service JWT is authenticated: the hook's caller by its service key, the token endpoint's caller by Keycloak.

None of the three names Kubernetes. Where the hook runs is a placement choice, made per API by where its traffic enters.

  • APIs swap the Keycloak issuer for the service's issuer in their existing config (issuer-uri, Authority, oidc.NewProvider) and nothing else. The claim shape is the same as today, so role-reading code stays.
  • Keycloak is still the login page, the user store, the client store and where roles are assigned. Sessions get the same live treatment as tokens: roles are re-read on each resolve, so a revoked role reaches an interactive session within the cache window.
  • The service accepts any valid token of the realm as a session, which is what every API does today, and passes azp through unchanged. The one strict audience check is on its own self-service routes: minting API tokens and reading user data need a token issued for the service, so a token taken from a frontend cannot create API tokens.

The fork this creates for the content API. Keycloak's UMA endpoint only evaluates a Keycloak access token, which content never sees behind the hook, for sessions either. So content gets its permissions from the identity service for all traffic, which makes the role-based evaluator in internal/uma the only evaluator rather than a shadow of Keycloak's. Keycloak's Authorization tab becomes a config editor whose output the service reads. The alternative is to keep the 47-row role-to-permission table in content itself and drop UMA. bdp-core's bdp:// resources raise the same question.

Costs accepted. One in-cluster hop on every API request through the ingress, anonymous ones included (3 ms warm, 95 ms cold for content). The service and its database are on the path of every request. Its signing key is the master key, so rotation is required rather than nice to have. The JWT must mirror Keycloak's claims faithfully, azp included, for the APIs' existing checks to keep working.

The JWT the APIs receive

The topology needs two things in the token: iss is the service and the signature is the service's. Everything else mirrors what Keycloak would have issued for that user, with the roles re-read, plus claims no existing API reads.

If users should be able to issue API tokens for parking, parking must accept the service's client in that check or switch to aud. If not, parking changes nothing beyond the issuer URL. That is parking's decision, not a requirement of the format.

Inside the cluster

Most writes never touch the ingress. The collectors repository shows where in-cluster traffic goes and how it authenticates:

bdp-core is therefore a fourth resource server: Keycloak client odh-mobility-writer, an ADMIN role, its own UMA with bdp:// resource URIs, a public host mobility.share.opendatahub.com for outside pushers, and most of its traffic arriving over cluster DNS. The hook in ingress-nginx never sees that traffic. Under "trust only the service's issuer" those 48 writers would be rejected the moment bdp-core switches issuer; under "accept traffic only from the ingress" they would be cut off one layer lower.

Three ways to close it, and the choice:

  • Route through the ingress anyway. Point BDP_BASE_URL at the ingress controller's cluster service with the right Host header. Nothing new to build, 48 values files change, and every write pays a hop and a hook call for no gain, since the caller is a known machine client.
  • The token endpoint. Chosen. One value in the oauth-collector secret, rendered by cluster-secrets from oauthCollector.tokenUri in the environment files, moves 49 deployments at once. In-cluster calls stay in-cluster. The NetworkPolicy for bdp-core and ninja-api allows the collector namespace next to the ingress.
  • A pod-level hook. A mesh with ext_authz, or an nginx sidecar in the bdp-core pod. Correct, and far heavier than the problem.

bdp-core's UMA. Non-admin pushers are authorized by Keycloak resources in the bdp://station?origin=… form, evaluated with a Keycloak token that bdp-core will no longer see. The service's role-based evaluator would have to cover those policies too, or the grants move into bdp-core. Which policy types the writer actually uses has to be checked before the cutover; the service refuses to approximate anything that is not role-based.

Outside the cluster

For the cluster APIs, ingress-nginx is where the three conditions above are cheapest: their traffic already converges there, the service is one in-cluster hop away, a NetworkPolicy makes "only through the hook" true for the API and "only from the ingress" true for the forward-auth route, and the parking host that never touches Caddy is covered. Running the same hook on the Caddy VMs would miss parking, send every auth call out of the cluster and back, and need a hand-written .caddy file per host. A system elsewhere runs the hook at its own edge, against the service's public host, and the service authenticates that caller by its key header rather than by network position.

Browser frontends: no change

databrowser and discovery log in with keycloak-js (PKCE, check-sso, silent refresh every 6 s) and send the Keycloak access token to the content API. A static site on S3 does exactly the same. With the hook that stays as it is: the browser logs in at auth.opendatahub.com, gets a Keycloak token, sends it to tourism.api.opendatahub.com; the ingress hook verifies it as a session, re-reads the user's roles, and the API receives a service JWT. The frontend never sees the service, needs no new library and no new login. Where the SPA is hosted is irrelevant: S3, a docker host behind Caddy or the cluster, because the SPA has no server side and the hook sits in front of the API it calls, not in front of the site.

Two things must be true for that to work, and both are service-side:

  • Which Keycloak tokens the hook accepts. Any valid token of the realm, regardless of audience, because content runs with ValidateAudience=false and the SPA clients have no audience mapper. That is what every API accepts today. A per-API list of allowed frontends was considered and dropped: the databrowser calls content and mobility with one token, and each API already applies its own rule, parking's azp check included.
  • CORS on a 401. When the hook rejects a token, nginx answers the browser itself, without the CORS headers the API would have added, and the browser reports a CORS failure instead of a 401. Either the ingress adds CORS headers (ingress-nginx's enable-cors annotations) or the hook lets an invalid token through as anonymous and leaves the 401 to the API. The preflight itself carries no Authorization and resolves as anonymous.

The frontends still need Keycloak to be public, which every cleanup above preserves: only the admin paths get restricted.

A system with its own backend, outside the cluster

discovery is the concrete case: frontend, Go backend and chatbot in docker-compose on docker01, nginx in front, the backend validating Keycloak JWTs against Keycloak's JWKS and reading resource_access roles. It joins like the cluster APIs do, at its own edge. There is one flow for every API; what differs is only which proxy makes the hook call.

Part two · deployment

Today

Two edges exist already. The Caddy proxies on the proxyprod and proxytest VMs terminate TLS for every public host and forward plain HTTP to the cluster's ingress-nginx load balancer. The parking control tower bypasses Caddy: its host points straight at the ingress and cert-manager issues the certificate in the cluster. Pomerium runs in the cluster as a second ingress class for internal tools, logging users in at Keycloak.

Target, minimal

The hook goes in ingress-nginx, not in Caddy. nginx's auth_request is a stock ingress-nginx annotation, it runs inside the cluster where the identity service lives, it covers the parking host that never passes through Caddy, and it survives the Scaleway migration unchanged because the Caddy-to-ingress shape is being reproduced there. Caddy keeps doing TLS and nothing else.

Why not the other two edges

  • Caddy. It sits on VMs outside the cluster, so every auth call would leave the cluster and come back. Parking does not pass through it. The ansible-caddy-sites role has no forward_auth option, so each API would need a hand-written .caddy file like mobility.api.opendatahub.com.caddy.
  • Pomerium. Built for browser login to internal tools and already doing that job. It does not understand API tokens, it has its own load balancer, and anonymous public routes have to be explicitly opened. It would still need the identity service behind it.
  • Ory Oathkeeper. Only adds a hop here: ingress-nginx already speaks auth_request, which is what Oathkeeper's decision API would plug into.

Proposed: the same edge, with the clutter removed

The minimal target changes nothing it does not have to. Once the hook exists, three more moves make the picture simpler than today. Each is separable and can be skipped.

1 · TLS in the cluster for the API hosts

Parking already proves the pattern: DNS-01 cluster issuer, certificate in the Ingress, DNS straight at the load balancer. The commented lines in deploy/values/ninja-api/scaleway-test.yaml are exactly this. Doing it for the other hosts takes the OOM-prone proxy VM out of the API path and removes one hop. What moves with it: the /v2 prefix strip and the Swagger redirect in mobility.api.opendatahub.com.caddy become rewrite-target and permanent-redirect annotations, and API access logs come from ingress-nginx instead of Caddy's filebeat input. The Scaleway migration currently plans the opposite, so this is a decision to take there, not a detail.

2 · One hook for internal tools, no Pomerium

Pomerium exists to log a browser in at Keycloak and check a claim per host. The identity service resolves the same user and roles for every request already, so the per-host rule becomes a parameter of the hook (require=CLUSTER:ADMIN) and the internal tools move to the nginx ingress class. What the service lacks for this is a browser session: an OIDC redirect to Keycloak and a cookie, the part Pomerium and oauth2-proxy do. Until that exists Pomerium stays. Gone with it: a second ingress controller, a second load balancer and elastic IP, the authenticate.internal host, a Keycloak client and the flat roles mapper added for it.

3 · Keycloak behind the service

Keycloak keeps its public host, because browsers log in there and collectors fetch client_credentials tokens from it. Its admin console and admin REST API do not need to be public: a path rule on the Scaleway load balancer or a security group limits /admin and /auth/admin to the cluster and NOI addresses. The identity service is then the only thing that reads the realm.

User data: on demand, never in the JWT

The service stores what Keycloak cannot hold: settings, preferences, profile, one JSON object per namespace. None of it travels in the JWT. The JWT carries identity, roles, the principal kind, the token id and content's permissions, and nothing else, so it stays Keycloak-shaped and small. Whoever needs user data reads it when it needs it.

Who needs itHow it gets there
A frontend: settings page, profile, themeGET/PUT /v1/me/data/{namespace} with the user's session. Read once, written when the user saves.
An API whose answer depends on a preference, for API-token requests tooGET /v1/users/{subject}/data/{namespace} with its service key, the subject taken from the JWT, cached per subject for a few seconds. One in-cluster call, only from the endpoints that care.

Why not hydrate the JWT, which the PoC did at first:

  • Most consumers are frontends. A settings page calls /v1/me directly; routing the same data through an API on every request to reach a settings page is the wrong direction.
  • The JWT travels in a header. Content's permission list is already ~3 KB; preferences on top push against nginx's 8 KB header buffer, and every request pays for data most endpoints ignore.
  • Coupling. Hydration put the user-data store on the path of every request to every API, and tied the token service and the user-data service together. On demand, the hook never touches user data, and the two halves are independent.

Consequence for the service's shape. With hydration gone, the token half (tokens, resolve, forward-auth, the token endpoint, JWKS) and the user-data half (/v1/me/data, /v1/users/…/data) share only the Keycloak subject as a key and the same session check, which is a library call. They can stay one deployment or become two on organisational grounds alone: a split costs a second chart, secrets, database and rollout, and buys separate ownership and release cadence. The request path is unaffected either way.

The ingress hook, concretely

ingress:
  annotations:
    nginx.ingress.kubernetes.io/auth-url: "http://odh-iam.core.svc.cluster.local:4010/v1/forward-auth/timeseries"
    nginx.ingress.kubernetes.io/auth-response-headers: "Authorization"

nginx calls that URL once per request with the client's headers, and copies the Authorization header of the answer onto the request it forwards. The API never sees what the client sent.

Two things the dev stack gets away with that production cannot. The dev edge writes the service key into its nginx config. Helm values live in public repositories, so no key can go in an annotation; ingress-nginx's auth-proxy-set-headers annotation names a ConfigMap whose headers are added to the auth call, and that ConfigMap can be rendered by cluster-secrets from sops like the other secrets. Failing that, the route is confined by NetworkPolicy and identifies the target API from the forwarded host. And the cutover of an API is atomic: the annotation and the issuer setting must change in the same deploy, because with only one of them the API rejects every request. Rollback is reverting that one values file.

What the edge buys

  • APIs know one issuer. Integration is an issuer URL.
  • API tokens, sessions and machine clients arrive at the API in one shape.
  • Keycloak is reachable from the cluster only by the identity service.
  • A role change in Keycloak reaches open sessions in seconds.

What it costs at runtime

  • One in-cluster round trip on every request, anonymous ones included. Measured 3 ms warm, 95 ms cold for content.
  • Keycloak's admin API is read for every active user every 15 s per replica.
  • The service and its database are on the path of every request to the four APIs, and of every token renewal in the cluster.
  • A 3 KB Authorization header for content users with many permissions.

Open

  • Content's permission source: served by the service, or a role table inside content with UMA dropped. The same for bdp-core's bdp:// resources, after an inventory of its policies.
  • Whether anonymous traffic bypasses the hook. Timeseries is mostly anonymous; a rule on the Ingress can skip the call when no Authorization header is present, if the API keeps its own anonymous default.
  • Whether the Scaleway migration keeps Caddy in front of the API hosts (cleanup 1).
  • When discovery's own nginx gets the hook. Every API joins; none stays on Keycloak directly.
  • Key rotation for the issuer: publish two keys in JWKS, sign with the newer.
